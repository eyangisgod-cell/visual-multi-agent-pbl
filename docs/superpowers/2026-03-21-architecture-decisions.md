## ADR-001: 采用混合架构（Next.js + Python AI 微服务）

**状态**: ✅ 已采纳

### 背景

需要选择一个技术栈，既要支持强大的 AI/Agent 能力（AG2 框架），又要提供优秀的用户体验（SSR、移动端优化）。

### 备选方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A: 纯 Python** | FastAPI 后端 + React 前端分离 | 技术栈统一在 Python 生态 | 前端 SSR 需要额外配置 |
| **B: 纯 Node.js** | Next.js 全栈 + AutoGen.js | 统一 TypeScript 语言 | JS 版 Agent 框架功能不完整 |
| **C: 混合架构** | Next.js 全栈 + Python AI 微服务 | 各自发挥优势 | 需要 RPC 通信 |

### 决策

选择 **方案 C：混合架构**

### 理由

1. **AG2 框架原生支持在 Python** - Group Chat 等核心功能 Python 最成熟
2. **Next.js 前端优势** - SSR 对移动端 SEO 友好，首屏加载快
3. **职责分离** - Next.js 处理业务 API，Python 专注 AI 能力
4. **独立扩容** - AI 服务可单独增加实例应对高峰

### 预期后果

- ✅ 开发效率：前后端统一 TS，AI 能力 Python 实现
- ✅ 性能：各自发挥优势
- ⚠️ 复杂度：需要设计 RPC 通信协议（HTTP/gRPC）

## ADR-002: 部署架构演进路线（Docker → 托管 K8s）

**状态**: ✅ 已采纳

### 背景

作为产品级 SaaS 平台，需要平衡早期开发效率和后期扩展性。

### 备选方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A: 微服务起点** | 一开始就按微服务设计 | 扩展性好 | 运维成本极高 |
| **B: 容器化单体** | Docker 单体，后期拆分 | 开发快，可演进 | 需要重构风险 |
| **C: Serverless** | 云函数 + 托管 DB | 按需付费，弹性好 | 冷启动问题，供应商锁定 |

### 决策

选择 **方案 B：容器化单体 → 托管 K8s 演进路线**

### 阶段规划

```
阶段 1 (MVP): Docker Compose 本地运行
阶段 2 (验证): 云服务器单机 Docker
阶段 3 (增长): 阿里云 ACK 托管 K8s
```

### 理由

1. **早期开发效率优先** - Docker Compose 最简单
2. **模块化设计** - 后期可按业务域拆分微服务
3. **成本可控** - 早期投入低，验证后再扩展
4. **技术债务可控** - 模块化好的话，拆分成本低

### 预期后果

- ✅ 阶段 1 开发成本最低
- ✅ 可根据业务增长灵活扩展
- ⚠️ 阶段 2→3 需要架构调整

## ADR-003: 使用 PostgreSQL + pgvector 作为向量检索方案

**状态**: ✅ 已采纳

### 背景

RAG 知识库需要向量检索能力，需要在 pgvector 和专用向量库之间选择。

### 备选方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A: pgvector** | PostgreSQL 插件 | 架构简单，混合查询强 | 大数据量性能一般 |
| **B: Milvus** | 专用向量数据库 | 性能最好，索引类型多 | 独立组件，运维复杂 |
| **C: Qdrant** | Rust 编写的向量库 | 性能好，API 友好 | 生态相对新 |

### 决策

选择 **方案 A：PostgreSQL + pgvector**

### 理由

1. **早期数据量小** - <500 万向量 pgvector 性能足够
2. **混合查询需求** - "年级筛选 + 语义检索"SQL+ 向量一体很方便
3. **架构简单** - 少一个组件，运维成本低
4. **可平滑升级** - 后期数据量大可引入 Milvus 做热数据缓存

### 预期后果

- ✅ 开发阶段无需学习新组件
- ✅ 混合查询（元数据 + 向量）SQL 原生支持
- ⚠️ 向量数>1000 万后需要评估迁移

## ADR-004: 使用 WebSocket + SSE + HTTP 混合通信协议

**状态**: ✅ 已采纳

### 背景

平台有多种通信场景（实时推送、流式输出、常规 CRUD），需要选择合适的通信协议。

### 备选方案

| 协议 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| **HTTP 轮询** | 常规 CRUD | 简单，防火墙友好 | 实时性差，服务器压力大 |
| **WebSocket** | 双向实时通信 | 延迟低，支持双向 | 需要维护连接状态 |
| **SSE** | 单向流式输出 | 比 WebSocket 简单 | 只支持单向 |

### 决策

采用 **混合协议：WebSocket + SSE + HTTP**

### 使用场景分配

| 场景 | 协议 | 理由 |
|------|------|------|
| 智能体移动同步 | WebSocket | 必须实时，双向 |
| 对话气泡显示 | WebSocket | 即时响应 |
| 流式输出（智能体回答） | SSE | 单向流，简单 |
| 通知推送 | WebSocket | 实时，可双向 |
| 常规 CRUD | HTTP | 足够，无状态 |

### 理由

1. **WebSocket 不可替代** - 智能体状态实时同步是核心体验
2. **SSE 适合流式输出** - 比 WebSocket 简单，浏览器支持好
3. **HTTP 用于常规请求** - 无状态，缓存友好

### 预期后果

- ✅ 用户体验最优（实时 + 流式）
- ⚠️ 需要维护多套通信逻辑
- ⚠️ 移动端断线重连需要处理

## ADR-005: 使用 Redis 作为缓存和实时数据层

**状态**: ✅ 已采纳

### 背景

平台需要缓存、会话管理、实时排行榜等功能，需要选择合适的缓存方案。

### 备选方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A: Redis** | 内存键值存储 | 功能丰富，生态成熟 | 需要额外组件 |
| **B: Memcached** | 简单缓存 | 性能略高 | 不支持丰富数据结构 |
| **C: 本地缓存** | 应用内存缓存 | 无额外组件 | 多实例无法共享 |

### 决策

选择 **方案 A：Redis**

### 使用场景

| 场景 | Redis 功能 | 说明 |
|------|-----------|------|
| 会话缓存 | String | 用户登录态 |
| 实时排行榜 | Sorted Set | 积分排行、作品热度 |
| WebSocket 状态 | Hash | 在线用户、房间管理 |
| 限流计数 | String + TTL | API 调用频率 |
| 响应缓存 | String + TTL | 高频问题 AI 回答 |
| 任务队列 | List | BullMQ 后端 |

### 理由

1. **功能丰富** - 支持 String、Hash、Set、Sorted Set 等多种数据结构
2. **持久化** - RDB/AOF 可选，数据不丢失
3. **生态成熟** - BullMQ、ioredis 等库完善
4. **发布订阅** - 支持 WebSocket 多实例通信

### 预期后果

- ✅ 满足所有缓存和实时数据需求
- ⚠️ 需要运维 Redis 实例
- ⚠️ 缓存一致性需要注意

## ADR-008: 登录认证采用渐进式方案

**状态**: ✅ 已采纳

### 背景

面向 K12 学生和家长，需要设计合适的登录方式。

### 备选方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A: 仅第三方登录** | 微信/QQ登录 | 体验好，免记住密码 | 需申请资质，审核周期长 |
| **B: 仅账号密码** | 传统登录 | 最简单 | 体验一般 |
| **C: 渐进式** | 账号密码 + 邀请码 + 第三方 | 灵活，可演进 | 实现复杂 |

### 决策

选择 **方案 C：渐进式方案**

### 阶段规划

| 阶段 | 登录方式 | 说明 |
|------|----------|------|
| **MVP** | 用户名/密码 + 昵称 + 邀请码 | 无需第三方资质 |
| **P1** | 增加微信登录 | 家长端，需申请资质 |
| **P1** | 增加 QQ 登录 | 学生端，需申请资质 |

### 邀请码机制

```
用户注册 → 生成个人邀请码 → 分享给朋友
                              ↓
朋友输入邀请码 → 验证通过 → 免密登录 → 绑定新账号
                              ↓
邀请人获得积分奖励
```

### 理由

1. **MVP 无需等待资质审核** - 可快速上线
2. **邀请码支持裂变传播** - 降低获客成本
3. **后期可平滑增加第三方登录** - 架构支持

### 预期后果

- ✅ MVP 可快速上线验证
- ✅ 邀请码机制支持增长
- ⚠️ 后期需要接入第三方登录

## ADR-009: 内容审核采用分层审核机制

**状态**: ✅ 已采纳

### 背景

面向 K12 学生的 UGC 平台，内容安全合规是红线。

### 备选方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A: 全 AI 审核** | 全部用 LLM/API审核 | 成本低 | 可能漏判 |
| **B: AI+ 人工** | AI 初审 + 人工复审 | 准确率高 | 成本高 |
| **C: 分层审核** | 按内容类型分级 | 平衡成本与风险 | 策略设计复杂 |

### 决策

选择 **方案 C：分层审核**

### 审核策略

| 内容类型 | 审核方式 | 说明 |
|----------|----------|------|
| **公开内容**（作品广场、智能体广场） | AI + 人工 | 先审后发 |
| **私人内容**（个人项目） | AI 抽查 + 举报 | 降低审核成本 |
| **评论互动** | AI 实时过滤 | 敏感词即时拦截 |
| **付费内容** | 人工审核 | 确保质量 |

### 技术方案

1. **阿里云内容安全 API** - AI 初审（文本、图片）
2. **人工审核后台** - 复审争议内容
3. **用户举报机制** - 事后监督

### 理由

1. **平衡成本与风险** - 不是所有内容都需要人工
2. **合规要求** - K12 平台必须严格审核
3. **用户体验** - 私人内容降低审核频率

### 预期后果

- ✅ 内容安全风险可控
- ✅ 符合监管要求
- ⚠️ 需要组建审核团队（或外包）

1. **开发成本可控** - 一套代码覆盖所有平台
2. **体验接近原生** - PWA 能力足够
3. **无需应用商店审核** - 快速迭代

### 预期后果

- ✅ 快速上线移动端

## ADR-011: RAG 采用混合检索策略

**状态**: ✅ 已采纳

### 背景

项目案例需要结合学科知识，需要设计高效的检索策略。

### 备选方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A: 纯向量检索** | 只用 Embedding | 简单 | 关键词匹配弱 |
| **B: 纯关键词检索** | BM25 | 精确匹配好 | 语义理解弱 |
| **C: 混合检索** | 向量 + 关键词 + 重排序 | 效果最好 | 实现复杂 |

### 决策

选择 **方案 C：混合检索（多路召回 + 重排序）**

### 检索流程

```
1. 用户提问
   ↓
2. Query 理解（意图识别 + 关键词提取）
   ↓
3. 多路召回:
   - 向量检索 (Top 50)
   - BM25 关键词检索 (Top 50)
   - 元数据过滤（年级/学科）
   ↓
4. 重排序：BGE-Reranker → Top 5
   ↓
5. 上下文组装 + Prompt → LLM 生成回答
   ↓
6. SSE 流式输出
```

### 理由

1. **检索效果更好** - 多路召回覆盖更广
2. **重排序提升精度** - Reranker 精排
3. **元数据过滤** - 年级/学科限定

### 预期后果

- ✅ 检索准确率高
- ⚠️ 实现复杂度增加
- ⚠️ 需要调优（权重、阈值）
