## 一、项目概述

### 1.1 项目定位

面向 K12 学生的**项目式学习（PBL）SaaS 平台**，通过游戏化界面和多智能体协作，激发学生内驱力，培养未来核心能力。

### 1.2 核心价值主张

| 问题 | 解决方案 |
|------|----------|
| 学生对学习没兴趣 | 游戏化体验 + 角色扮演（CEO）激发成就感 |
| 缺乏自驱力 | 任务闯关 + 作品 PK + 积分等级激励机制 |
| 被动学习 | 学生主动调度智能体，培养决策判断能力 |
| 知识脱离实际 | 项目式学习，结合学科知识解决真实问题 |

### 1.3 目标用户

- **主要用户**: K12 学生（小学三年级至高中）
- **次要用户**: 家长（付费决策者）、教师（班级管理者）
- **部署模式**: C 端 SaaS 平台，支持大规模并发用户

## 二、核心功能设计

### 2.1 学生端功能

#### 2.1.1 首页/任务选择
- 按年级筛选（小学/初中/高中）
- 按类型筛选（科学/工程/艺术/社会科学）
- 闯关模式（完成上一关解锁下一关）
- 挑战模式（PK 赛、限时任务）

#### 2.1.2 游戏化任务界面
- **像素风虚拟世界**: 2D 俯视角，类似模拟城市
- **智能体可视化**:
  - 不同人格形象（导师/设计师/分析师/运营师等）
  - 移动动画（走到工位、协作位置）
  - 气泡对话框（实时显示对话）
  - 思考过程可视化（可选开关）
- **右侧对话面板**:
  - 完整对话历史记录
  - @智能体提及功能
  - 群聊通知所有智能体

#### 2.1.3 智能体系统
- **平台预设智能体**: 核心教学角色（保证质量）
- **进阶定制智能体**: 基于模板调整专业方向
- **原创智能体**: 从 0 创建（需达到一定等级解锁）
- **AI 辅助创建**: 描述需求，AI 生成配置后微调
- **智能体考核**: 任务完成效果评价，淘汰/替换

#### 2.1.4 作品系统
- 作品生成（文本/图片/3D 模型）
- 作品广场（点赞、评论、分享）
- 个人中心（作品集、评论历史、积分等级）
- 微信分享（生成链接/小程序卡片）

#### 2.1.5 个人中心
- 个人信息（昵称、头像、年级）
- 我的作品集
- 我的评论
- 积分/等级/能力雷达图
- 我的智能体（创建/收藏）

### 2.2 管理后台功能

#### 2.2.1 项目管理
- 上传项目任务（富文本编辑器）
- 项目模板库
- AI 辅助生成项目（对话式创建）
- 项目配置（年级、学科、难度、前置任务）

#### 2.2.2 RAG 知识库管理
- 学科知识库上传（PDF/Word/Markdown）
- 知识图谱编辑
- 语义检索测试
- 向量索引重建

#### 2.2.3 智能体配置
- 智能体模板管理
- 人格配置（soul.md/agent.md）
- 记忆配置（memory.md/user.md）
- 技能/工具绑定

#### 2.2.4 内容审核
- 作品审核（AI 初审 + 人工复审）
- 评论审核
- 智能体审核（公开前）
- 举报处理

#### 2.2.5 数据分析
- 用户活跃看板
- 任务完成率分析
- 智能体调用统计
- 付费转化漏斗

## 三、架构设计决策

### 3.1 为什么选择混合架构（Next.js + Python AI）

| 考量维度 | 纯 Python 方案 | 纯 Node.js 方案 | **混合架构（选定）** |
|----------|---------------|----------------|---------------------|
| AG2 框架支持 | ✅ 原生完整 | ⚠️ JS 版滞后 | ✅ Python 服务独享 |
| 前端体验 | ⚠️ 分离部署复杂 | ✅ SSR 内置 | ✅ Next.js 原生 |
| 开发效率 | ⚠️ 双语言栈 | ✅ 统一 TS | ⚠️ 需 RPC 通信 |
| 部署复杂度 | 中 | 低 | 中 |
| 扩展性 | 中 | 中 | ✅ 服务独立扩容 |

**决策理由**:
1. AG2 核心功能（Group Chat）Python 最成熟，不可妥协
2. Next.js 提供 SSR 对移动端 SEO 友好，首屏加载快
3. 职责清晰：Next.js 处理业务逻辑，Python 专注 AI 能力
4. 可独立扩容：AI 服务可单独增加实例应对高峰

### 3.2 为什么选择容器化单体 → 托管 K8s

| 阶段 | 部署方案 | 理由 |
|------|----------|------|
| **开发/测试** | Docker Compose | 简单，一个 YAML 搞定本地环境 |
| **MVP 验证** | 单机 Docker | 成本最低，快速上线验证 |
| **产品运营** | 阿里云 ACK（托管 K8s） | 自动弹性伸缩，应对学生使用高峰 |
| **大规模** | 多区域 K8s + 边缘节点 | 降低延迟，提升用户体验 |

**演进路径**: 本地 Docker → 云服务器 → 托管 K8s → 边缘计算

**为什么不用微服务起点**:
- 团队规模有限，微服务运维成本过高
- 业务边界尚未清晰，过早拆分增加复杂度
- 模块化设计好，后期可按业务域拆分微服务

### 3.3 为什么选择 PostgreSQL + pgvector 而非 Milvus

| 维度 | pgvector | Milvus | 选择理由 |
|------|----------|--------|----------|
| 架构复杂度 | 低（PG 插件） | 高（独立服务） | 早期少一个组件 |
| 数据规模 | <5000 万向量 | >1 亿向量 | MVP 阶段数据量小 |
| 混合查询 | ✅ SQL+向量一体 | ⚠️ 需额外处理 | 年级 + 语义检索需求 |
| 运维成本 | 低 | 高 | 小团队优先 |
| 升级路径 | 可平滑迁移 Milvus | - | 后期可替换 |

### 3.4 为什么选择 Redis 作为缓存层

**使用场景**:
1. **会话缓存**: 用户登录态、智能体对话上下文
2. **实时排行榜**: 积分排行、作品热度排行
3. **WebSocket 状态**: 在线用户、房间管理
4. **限流计数器**: API 调用频率限制
5. **响应缓存**: 高频问题 AI 回答缓存

**为什么不用其他方案**:
- Memcached: 不支持丰富数据结构
- 本地缓存: 多实例无法共享
- Redis 集群：成熟稳定，社区活跃

### 3.5 为什么需要 WebSocket

| 场景 | HTTP 轮询 | WebSocket | 选择理由 |
|------|----------|-----------|----------|
| 智能体移动同步 | ❌ 延迟高 | ✅ 实时 | 必须实时 |
| 对话气泡显示 | ❌ 体验差 | ✅ 即时 | 必须实时 |
| 通知推送 | ⚠️ 延迟高 | ✅ 实时 | 必须实时 |
| 流式输出 | ⚠️ SSE 单向 | ✅ 双向 | 更灵活 |

**WebSocket 不可替代**: 智能体状态实时同步是核心体验，必须使用。

## 五、部署架构演进

### 5.1 阶段一：本地开发（Docker Compose）

```yaml
# docker-compose.dev.yml
services:
  nextjs-app:
    build: ./frontend
    ports: ["3000:3000"]
    volumes: ["./frontend:/app"]

  python-ai:
    build: ./backend/ai-service
    ports: ["8000:8000"]
    volumes: ["./backend/ai-service:/app"]

  postgres:
    image: pgvector/pgvector:pg16
    ports: ["5432:5432"]
    environment:
      POSTGRES_DB: pbl_platform
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

  minio:
    image: minio/minio
    ports: ["9000:9000", "9001:9001"]
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: minioadmin
      MINIO_ROOT_PASSWORD: minioadmin123
```

**特点**:
- 无需证书、CDN
- MinIO 开源对象存储
- 所有服务本地运行
- 适合开发调试

### 5.2 阶段二：云服务器（单机 Docker）

- 购买云服务器（2C4G 或 4C8G）
- 使用 Docker Compose 部署生产环境
- 配置 Nginx 反向代理
- 申请免费 Let's Encrypt 证书

### 5.3 阶段三：托管 K8s（阿里云 ACK）

- 多副本部署，自动弹性伸缩
- RDS 高可用 PostgreSQL
- Redis 集群版
- OSS + CDN 全球加速

## 六、登录认证设计

### 6.1 登录方式优先级

| 登录方式 | 阶段 | 说明 |
|----------|------|------|
| **用户名/密码** | P0（MVP） | 最简单，无需第三方 |
| **昵称 + 邀请码** | P0（MVP） | 裂变传播，免密登录 |
| **微信登录** | P1 | 家长端，付费场景 |
| **QQ 登录** | P1 | 学生端，分享场景 |

### 6.2 邀请码机制

```
用户注册 → 生成个人邀请码 → 分享给朋友
                              ↓
朋友输入邀请码 → 验证通过 → 免密登录 → 绑定新账号
                              ↓
邀请人获得积分奖励
```

## 七、待解决问题清单

### 7.1 技术风险

| 问题 | 影响 | 缓解措施 | 负责人 |
|------|------|----------|--------|
| AG2 框架成熟度 | 高 | 预留 AutoGen 备选，定期评估 | - |
| PixiJS 移动端性能 | 中 | 降级策略（低帧率/简化渲染） | - |
| LLM 响应延迟 | 高 | 流式输出 + 高频问题缓存 + 预生成 | - |
| WebSocket 移动端断线 | 中 | 自动重连 + 状态同步机制 | - |
| pgvector 大数据量性能 | 中 | 定期评估，超过 1000 万向量迁移 Milvus | - |

### 7.2 产品问题

| 问题 | 说明 | 待决策 |
|------|------|--------|
| 智能体创建门槛 | 太低导致质量参差，太高影响活跃度 | 是否需要等级限制？ |
| 作品审核标准 | 如何定义"合格作品"？ | 需要教研团队制定标准 |
| 闯关难度曲线 | 如何动态调整？ | 需要学习数据积累 |
| 积分通胀风险 | 积分贬值影响激励效果 | 需要经济系统设计 |

### 7.3 合规问题

| 问题 | 说明 | 缓解措施 |
|------|------|----------|
| K12 数据隐私 | 未成年人信息保护 | 符合《未成年人保护法》 |

| 支付合规 | 面向未成年人付费 | 家长确认机制 |
| 算法备案 | AI 生成内容 | 按监管要求备案 |

### 7.4 运营问题

| 问题 | 说明 |
|------|------|
| 冷启动内容 | 首批项目案例需要专业团队制作 |
