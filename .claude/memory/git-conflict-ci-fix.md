## 冲突处理流程

### 当前配置（手动修复）
1. `conflict-check.yml` 每天检测冲突
2. 创建 GitHub Issue 通知
3. **需要手动解决冲突**

### 期望的自动化流程
1. 检测冲突 → 创建 Issue
2. 自动创建新分支修复冲突
3. 尝试自动合并（简单冲突）
4. 无法自动解决时通知人工

**Why**: 用户询问能否自动获取 Issue 并自动修复冲突

**How to apply**:
- 简单冲突（不同文件修改）可以自动合并
- 复杂冲突（同文件同行修改）需要人工介入
- 修复后创建新分支和 PR

## CI 失败处理

### 当前问题
- CI 失败后没有自动修复机制
- 需要人工查看错误日志

### 期望的自动化
1. CI 失败 → 获取错误日志
2. 分析错误类型（ESLint/TypeScript/Test）
3. 自动修复可修复的问题
4. 重新推送触发 CI

**Why**: 用户询问能否自动获取 CI 失败原因并修复

**How to apply**:
- ESLint 错误：使用 `eslint --fix` 自动修复
- TypeScript 错误：需要人工修复（类型问题）
- 测试失败：需要人工修复（逻辑问题）

## 本地 CI 验证

### 当前问题
- 提交前不运行本地检查
- 依赖远程 CI 发现错误

### 期望的配置
- Pre-commit hook 运行快速检查
- ESLint/TypeScript 本地验证
- 单元测试本地运行

**Why**: 用户询问为什么不本地先跑 CI 再提交

**How to apply**:
- 配置 husky pre-commit hook
- 运行 lint 和 type check
- 可选：运行相关测试

## PR 管理策略

### 问题
- CI 成功后自动合并到 main
- 本地继续修改同一分支会造成混乱

### 建议流程
1. CI 成功 → 自动合并到 main
2. 本地基于最新 main 创建新分支
3. 新分支创建新 PR

**Why**: 用户询问提交后 CI 成功自动合并，本地继续修改是否创建新 PR

**How to apply**:
- 合并后删除已合并的 feature 分支
- 基于 main 创建新分支继续开发
- 避免在同一分支累积过多更改
